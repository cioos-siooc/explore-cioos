# Incremental update v2 — delta-proportional loads, live site during rebuilds

Follow-up to `incremental-update-performance.md`. That doc's items **C** (no DDL
in the load path), **D** (partial) and **E** (timeouts, advisory lock) are now
implemented. This doc covers what is still broken and the plan to finish the
job, including the two remaining operational problems:

1. **The site still degrades to 504s during a load** — no longer because of
   `ACCESS EXCLUSIVE` locks, but because the processing phase is still a
   *global* rebuild that saturates the DB host.
2. **Concurrent harvesters queue for tens of minutes** — every loader
   serializes on the advisory lock around `process_incremental_update()`, and
   that critical section is minutes long because of (1).

## Why it still blocks

The ingest side of the incremental path is genuinely incremental (temp tables,
COPY, delta upserts). The **processing** side is not:

- `profile_process()` (`database/5_profile_process.sql:68`) still runs
  `DELETE FROM cde.points` and reinserts every distinct geometry with **new
  serial pks** on every run — even a single-server harvest.
- Because `points` pks are renumbered each run, every dependent table must be
  fully relinked every run: `obis_link_point_pk()` rewrites **all** obis_cells,
  and `create_hexes()` (`database/4_create_hexes.sql:66`) rewrites **all**
  ~778k trajectory_cells by geometry join.
- `create_hexes()` still deletes both hex tables and re-tiles the entire data
  extent at 100 km and 10 km via `ST_HexagonGrid(... ST_EstimatedExtent ...)`,
  then runs four more full-table `UPDATE` passes over `points`, `profiles`,
  `obis_cells`.

Net effect: a one-dataset delta still rewrites millions of rows inside one
transaction. Readers aren't lock-blocked anymore, but the IO/CPU/WAL storm plus
autovacuum makes every query slow, the web-api's knex pool (still the default,
max 10, no explicit config — old item E leftover) exhausts, and the frontend
504s. Meanwhile any other harvester sits waiting on
`DB_LOADER_ADVISORY_LOCK_KEY` for the whole rebuild.

## Design principles

- **Stable identity everywhere.** Nothing gets renumbered on a routine load.
  If pks are stable, "relink the world" passes disappear and work becomes
  proportional to the delta.
- **Precompute at harvest / insert time.** A value that is a pure function of
  the row (geom, days, hex cell) is computed once when the row is created,
  never by a post-hoc full-table `UPDATE`.
- **Global rebuilds never run against the serving schema.** Full reloads build
  in a shadow schema and swap.

## Plan

### 1. Stable, insert-time hex assignment (enabler) — ✅ DONE

PostGIS hex grids are **origin-anchored**: `ST_Hexagon(size, i, j)` /
`ST_HexagonGrid` place cell (i,j) deterministically relative to the SRS origin
— the `bounds` argument only selects which cells are emitted. (Verified
empirically on our PostGIS 3.1: identical cell geoms across different bounds;
degenerate point bounds return the covering cell.) So a point's hex cell is a
pure function of its geometry:

- Add an `IMMUTABLE` SQL function `hex_cell(geom, size) → (i, j)` (closed-form
  math, no spatial join), and use `ST_Hexagon(size, i, j)` when the polygon is
  needed.
- Re-key `hexes_zoom_0/1` with a natural key `(i, j)` + `UNIQUE`; keep the
  serial pk for the existing FK/tile queries. Newly occupied cells are added
  with `INSERT … ON CONFLICT (i, j) DO NOTHING` — existing pks never change.
- `points` stores `hex_0_pk` / `hex_1_pk` computed **at insert time** (resolve
  `(i,j)` → pk after the hex upsert). Drop the per-point
  `hex_zoom_0/hex_zoom_1` polygon columns entirely.
- Migration turned out even cheaper than expected: because the old grid was
  generated by the same origin-anchored functions, existing hex rows already
  align with the global tiling — `migrations/stable-hex-grid.sql` backfills
  `(i, j)` **in place**, no renumbering, no cache invalidation needed.

Implemented as `hex_cell()` + rewritten `create_hexes()` in
`4_create_hexes.sql`. Measured on the dev DB (62k points, worst case with
every point unassigned): 12.5 s total, hex pks bit-stable, assignments
identical to the old spatial-join output.

### 2. Append-only `points`, no renumbering — ✅ DONE

- Add `UNIQUE (geom)` on `cde.points`; replace the `DELETE FROM cde.points` +
  rebuild with the insert-missing anti-join pattern that
  `obis_insert_points()` / `trajectory_insert_points()` already use.
- Since pks are now stable, all "relink point_pk for every row" passes shrink
  to `WHERE point_pk IS NULL` (their original intent — see the comment on
  `obis_link_point_pk()` explaining it only relinks all rows *because* points
  get renumbered).
- Orphaned points/hexes (no remaining referrers after a dataset shrank) are
  garbage-collected **out of band**, post-commit next to the existing
  post-load `VACUUM ANALYZE` — never inside the load transaction.

Implemented: `migrations/append-only-points.sql` (unique index only — existing
rows/links need no backfill), `profile_process()` insert-missing +
NULL-scoped relinks, hex-FK propagation in `create_hexes()` scoped to
unlinked rows, `gc_orphan_points_and_hexes()` run by the db-loader
post-commit under a try-advisory-lock. Measured on the dev DB: a zero-delta
incremental (`process_incremental_update()` with empty temp tables) runs in
**4.4 s** with zero rows written; a same-data re-harvest of the two biggest
datasets (59k profiles + 624k trajectory cells) relinks every replaced row to
bit-identical point/hex pks with **zero writes outside the delta**; GC removes
exactly the predicted orphans and nothing else.

### 3. Delta-scope every processing step — ✅ DONE

Every function called by `process_incremental_update()` gets scoped to the
datasets present in `temp_datasets`:

- `profile_process()`: relink/`days`/`n_profiles` only for the changed
  datasets (`n_profiles` via a `GROUP BY` over just those dataset pks).
- `create_hexes()` collapses to: upsert newly occupied hex cells, link
  `hex_*_pk` for **new** points only, propagate FKs only to rows of changed
  datasets.
- `obis_*` / `trajectory_*` backfills already use `IS NULL` guards — they
  become genuine ~0-row no-ops once nothing is renumbered.

With 1–3, the advisory-locked critical section drops from minutes to seconds.
Concurrent harvesters still serialize (keep the single global lock — it's
simple and correct) but the queue drains in seconds per loader, and the DB
churn that caused 504s is gone at the root.

Implemented as: `WHERE point_pk IS NULL` scoping on
`obis_insert_points()`/`trajectory_insert_points()` (the DISTINCT+transform
scans over the full cells tables were 850 ms + 420 ms per load);
`IS DISTINCT FROM` no-op guards on every `datasets`/`organizations` UPDATE
(`n_profiles`, `pk_url`, `organization_pks` — the latter's `array_agg` now
ordered so the guard can't flap); and an OBIS gate in
`process_incremental_update()` — the scientific-name matviews read only
`scientific_names`/`n_records`, so their full refresh (1.2 s and growing with
OBIS volume, the largest fixed cost) now runs only when the load actually
touched OBIS data, with the cheap aphia backfill kept on every load.
Measured: a zero-delta incremental is **0.6 s** with zero rows written to any
table; a same-data OBIS re-harvest (25k cells) takes 6.8 s with bit-identical
links; a brand-new location correctly creates its point + hex end-to-end.

### 4. Precompute at harvest level — descoped (made moot by 1–3)

Already done: generated `geom` on cells tables, `days` at harvest for
trajectories, `dataset_pk` at COPY/insert time, `aphia_ids` at COPY time.

The rest of this step was motivated by shrinking the DB critical section —
but with 1–3 done, everything it would move to the harvester (`days` on
profiles, `n_profiles`, hex assignment) is already computed only for the
delta, in milliseconds-to-subsecond SQL passes with no-op write guards. Moving
them to Python would touch the CSV contract (Pandera schemas, loader) for no
measurable gain and would split the hex math across two languages. Revisit
only if a profiler ever shows these passes mattering again.

### 5. Full rebuilds go blue/green (site stays live) — routine case ✅ DONE

Routine case: once incremental is delta-proportional, the nightly "full"
refresh can simply **be** an incremental run covering all sources plus the
out-of-band GC — no TRUNCATE at all.

Implemented as `prune_stale_datasets()` (`9_incremental_upsert.sql`), called
by the db-loader at the end of every incremental load (disable with
`CDE_PRUNE_STALE=0`). A harvest fully enumerates each source it covers —
changed → `temp_datasets`, unchanged → `temp_verified`, errored/filtered →
`temp_skipped_datasets` — so a DB dataset of a covered source appearing in
none of the three is gone upstream and is deleted with its profiles/cells
(orphaned points/hexes/organizations follow via the post-commit GC;
`datasets_lookup` stays append-only so pk_url survives a dataset returning).
A per-source guard refuses to prune more than 50% of a source in one run
(harvester bug / partial enumeration protection). With that,
**`harvest_config.production.yaml` is flipped to `incremental: True`** — the
production schedule no longer TRUNCATEs, so routine "rebuilds" stop taking
the site down entirely. The full-reload path remains for disaster recovery /
schema rebuilds only.

True rebuilds (schema changes, `recreate_database.sh`): build into a shadow
schema while `cde` keeps serving, then swap:

```sql
BEGIN;
ALTER SCHEMA cde RENAME TO cde_old;
ALTER SCHEMA cde_next RENAME TO cde;
COMMIT;  -- sub-second; only momentary locks on the schema names
```

The web-api queries are `cde.`-qualified plain queries via knex, so new
requests resolve the new schema immediately; flush the apicache tile/legend
cache after the swap. Drop `cde_old` after verification.

### 6. Guardrails (cheap, do anytime)

- ✅ Explicit knex pool config in `web-api/db.js` (`min`/`max` via
  `DB_POOL_MIN`/`DB_POOL_MAX`, `acquireTimeoutMillis: 30000`) so a slow DB
  degrades instead of hard-failing — the one item E leftover.
- ✅ Autovacuum tuning on the load-churned tables (`profiles`, `obis_cells`,
  `trajectory_cells`, `points`): `autovacuum_vacuum/analyze_scale_factor =
  0.02` so cleanup runs small-and-frequent instead of bursting IO against
  live traffic (`migrations/autovacuum-churned-tables.sql`).
- ✅ Loader deprioritization: the incremental session sets
  `max_parallel_workers_per_gather = 0` so merge-phase scans stay on one core
  and can't starve public web-api queries; the full-reload path keeps
  parallelism (it runs with the site down).

## Suggested order

1. (6) guardrails — independent, ship now.
2. (1) hex grid natural key + insert-time assignment (+ migration).
3. (2) append-only points.
4. (3) delta-scoping of the processing functions.
5. (4) harvest-side precompute of the remaining derivables.
6. (5) shadow-schema swap for true rebuilds; retire routine TRUNCATE reloads.

## Acceptance criteria

- Single-source incremental load: shared-table critical section (advisory lock
  hold time) measured in **seconds**; runtime proportional to the delta.
- Frontend p95 latency unaffected while a load runs; no 504s.
- Two harvesters submitting simultaneously: second finishes within seconds of
  the first, not minutes.
- `points`/`hexes` pks stable across runs (snapshot pks, re-harvest an
  unchanged source, diff — zero changes).
- Full-reload (shadow) and incremental paths produce identical derived tables
  (regression test).
- Site serves continuously through a full rebuild + swap.
